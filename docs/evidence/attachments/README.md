# Composer menu and SSH attachment acceptance

2026-10-21. This feature belongs to the sample app; the transport-independent terminal AAR is unchanged.

- [Physical Xiaomi / API 36](phone-api36-tests.txt): all eight AttachmentTest checks passed. Three opt-in checks used the existing pinned SSH profile to the local Mac over Tailscale: streamed document upload with matching remote SHA-256 and mode 0600, rejection after removing every matching host pin, and a file-picker result surviving Activity recreation with the path inserted exactly once at the saved draft cursor. These tests do not submit terminal input; disposable upload files and temporary untrusted profiles are removed.
- [API 27](api27-tests.txt) and [API 35](api35-tests.txt): five local checks each passed; the three saved-host-dependent checks were skipped. Local coverage includes keyboard-open/closed/reflow positioning, landscape edge clamping, Unicode/path-safe names, unknown-length stream bounds, invalid sources, declared oversize and cancellation without publishing a path.
- The automated picker test intercepts ACTION_OPEN_DOCUMENT with a synthetic content URI. Separately, the user selected and explicitly sent an image through the actual physical picker; its remote file path appeared in Claude Code. This was confirmed as manual sending, not an automatic upload action. The user's image is retained. No private image or QR content is included in this evidence.
- Replacement installation and final acceptance preserved all fifteen original preference/encrypted-profile files byte-for-byte. [Sanitized comparison](data-preservation.json). Debug, test APK, R8 release APK and debug lint builds passed. The final debug APK is installed on the phone. No tag, GitHub release or Maven publication.

The test-only document provider lives in the instrumentation APK. Debug builds declare its visibility; release builds contain neither the provider nor that query. Xiaomi autostart restrictions required the runner to start this synthetic provider through a shell query before the tests, without changing device autostart settings. The existing debug restriction-probe receiver remains intact.

Private screenshots stay under build/attachments/. Initial runs found and fixed lost draft selection during recreation and delayed IME focus after popup dismissal. A host-key test initially changed only one of several trusted keys; its corrected fixture removes all matching pins. Landscape assertions allow the bubble to move inward at the window edge rather than requiring it to extend offscreen.

## Reference interaction observed on Moshi Android 4.1.0

A fresh pairing to the current LAN Mac succeeded after an earlier cloud status request returned HTTP 500. The reference app was previously in Zen mode; standard toolbar mode was temporarily selected for inspection, then Zen mode was restored and its selected state verified.

The actual Add attachment panel is a dimmed bottom sheet with a drag handle, a title and three spaced rounded rows: Camera (capture a new photo), Photos or videos (select media), and File (upload to the host). An attached video appears as an approximately 64 dp square preview above the composer text, with a play affordance and a separate remove button. The send button is enabled with the attachment alone; the path is not displayed as editable composer text. This identified an interaction gap in the initial upload implementation. The 2026-10-22 implementation and acceptance below supersede that gap. These observations do not claim parity or prove every reference source's end-to-end transport.

Reference documentation: https://getmoshi.app/docs/image-paste and https://getmoshi.app/docs/files . The documents also describe iOS behavior; the three source rows and staged video preview above were observed separately on the Android phone. Reference screenshots remain private under build/attachments/.

## Staged attachment acceptance — 2026-10-22

The sample now uses the three-source sheet and staged cards described above. Phone panels meet the bottom edge; larger windows keep a bounded centered panel, and short landscape windows scroll the source rows. Images honor EXIF orientation and are decoded to at most 512 px on their longest side; video frames are bounded to 256×256. Missing/corrupt previews fall back to a document/media icon. Per-tab selection is limited to four, with two worker threads globally. Each card has a separate accessible remove target. Uploads do not change the draft or submit terminal input.

- [Physical API 36 attachment suite](staged-phone-tests.txt): twelve tests passed. Four opt-in host checks use temporary encrypted clones of an existing pinned profile, leaving the original profile intact. The fixture verifies document SHA-256/mode 0600, removes every matching pin to reject an untrusted host, survives Activity recreation with draft selection preserved, switches tabs without moving attachments, and captures the exact explicit-send bytes without sending the fixture path to the user's shell. The media check intercepts real picker/camera intents with synthetic PNG/MP4/JPEG results, verifies previews and remote uploads, checks private camera cleanup and removes a card through its actual button. Camera permission was already granted; its result branch executed. Temporary tabs/profiles and completed synthetic upload files are removed.
- [API 27](staged-api27-tests.txt) and [API 35](staged-api35-tests.txt): eight local checks passed per device, four host-dependent checks skipped. Local coverage includes portrait/landscape sheets, keyboard transitions, Unicode names, oversize/unknown-length limits/cancellation, EXIF rotation, narrow camera URI access and actual image/video decoding. API 27 uses `MediaMetadataRetriever.release()` rather than the newer AutoCloseable API.
- [Phone](paste-phone-api-tests.txt), [API 27](paste-api27-tests.txt), [API 35](paste-api35-tests.txt): six terminal API tests each passed, including bracketed mode enable/disable, UTF-8/multiline input, control stripping, empty paste, and a separate Enter.
- [Codex phone submission](codex-submit-tests.txt) and [Claude phone submission](claude-submit-tests.txt): each opt-in real SSH TUI check passed in a caller-created private tmux server. The original literal burst remained in Codex's input; bracketed paste plus Enter submitted it. The repaired phone composer submitted a Chinese/multiline/complex-emoji request to each CLI. Codex produced the requested reply marker. Claude showed an upstream API error after submission, so only submission is accepted for Claude. Its model response remains externally blocked. The test server is separate from all user tmux sessions and is stopped after inspection.
- [Data comparison](staged-data-preservation.json): fifteen original preference/encrypted-profile files remain byte-identical after replacement installation and regression. No private UI trees, QR material, access tokens or user media are committed. Screenshots stay in ignored `build/attachment-staging/`.

The new terminal paste API changes the AAR as well as the sample; debug/test builds, the release AAR, R8 release APK and debug lint passed. No tag, public release or Maven publication. Staged drafts remain service-lifetime state; process-death recovery and automatic remote file retention/cleanup are not implemented.

The Xiaomi fixture provider was initially killed under memory pressure. The runner now holds a stable provider client for each test instead of changing device autostart or battery settings. An API 27-only fixture constructor was also corrected before final acceptance. These harness repairs are separate from the Codex submission fix.
