# Tailscale discovery and pairing

Available in builds from `main` after alpha06. The alpha06 GitHub APK does not include this feature. Existing saved profiles and encrypted credentials are not migrated or rewritten.

## Discovery

Open **+ → Use your own SSH → Discover servers** with Tailscale connected on the phone.

- Read explicit IPv4 `/32` host routes from a VPN that has a Tailscale-range interface address. Ignore local addresses, MagicDNS, subnet routes and IPv6 routes. API 33+ also filters unreachable route types; older versions rely on the same TCP/SSH verification.
- Supplement these candidates with `tailscale status --json` over up to four saved SSH endpoints, prioritizing the active profile. These auxiliary commands use existing authentication and strict host-key verification. They do not send input into a terminal session or modify a remote configuration.
- Include the source computer and online peers, deduplicate addresses, and probe at most 128 candidates on TCP 22. Require an SSH identification banner before showing a result. Use the phone's default VPN route. LAN targets remain bounded by the Wi-Fi subnet; when a VPN is active, their probes also respect its routing policy instead of trying to bypass it. Without a VPN they stay bound to Wi-Fi. VPN-routed LAN probes allow 900 ms for connection and 1500 ms for the banner, within the existing overall scan limit.
- Display the Tailscale device name when available, otherwise use a MagicDNS PTR name or the IP. Rows are labeled `Tailscale` or `LAN`.
- Scan only while the setup screen is in the foreground, stop after 25 seconds, and cancel work when leaving the screen or changing networks. No Tailscale admin API credentials are needed or stored.

Android VPN route visibility varies. When only broad subnet routes are exposed, a fresh installation cannot enumerate the tailnet: first pair one computer or save a trusted SSH connection to a computer with the Tailscale CLI. The source computer's visible peer list and the phone's access rules can differ; only addresses the phone can reach on SSH are shown. Offline devices and SSH servers using other ports are not discovered; those can still be entered manually. This does not embed a Tailscale client or enable Tailscale SSH: it connects to the computer's existing SSH server through the VPN.

## Pairing

On the phone's pairing page, choose **Auto / LAN / Tailscale** and copy the command. The launcher supports:

```sh
curl -fsSL https://raw.githubusercontent.com/JackCaow/Shello/main/companion/pair.sh \
  | bash -s -- --network tailscale
```

`auto` (default) prefers a running local Tailscale client's IPv4 address, falling back to LAN when none is available. `tailscale` requires a connected client and does not silently fall back. `lan` skips Tailscale lookup. `--host` accepts a literal private LAN, loopback or `100.64.0.0/10` IPv4 address; an explicit network choice must agree with it. CLI lookup includes the macOS application binary, Homebrew and common Linux paths. IPv6-only and MagicDNS-hostname QR tickets are not supported in this version.

Keep both devices connected to the appropriate network. Tailscale access rules and host firewalls must allow the SSH port and temporary HTTPS pairing port; use `--port` if a fixed pairing port is required. The helper binds to the selected address, preserves existing authorized keys, and closes after pairing or expiry. The QR still pins the exact TLS certificate and authorizes one phone public key with a short-lived token. The app verifies SSH host keys and tmux before saving a separate connection. LAN profiles are not automatically changed to VPN addresses.

For the published alpha06 APK, use its matching launcher tag or `--network lan` with the new launcher.

## Validation (2026-10-21)

- macOS Tailscale client and Xiaomi Android phone were connected to the same tailnet. The phone found the Mac's SSH service through its actual VPN host route.
- A private QR image generated by the real helper was decoded through the app's image-scanning path, explicitly confirmed, and paired over the Tailscale address. The phone saved a new connection, executed a bounded SSH command, and checked the real tmux binary. Camera optics were not part of this check.
- LAN coexistence was checked with both local computers while the phone VPN remained connected.
- Original encrypted profile files were byte-for-byte unchanged. Original host `authorized_keys` entries were retained; pairing appended one phone public key.
- Python checks cover address boundaries, automatic/explicit network choice, CLI states/timeouts, generated launcher consistency, pinned TLS and token replay rejection. Android checks cover QR address boundaries, online peer parsing, bounds/deduplication and route filtering; opt-in device checks cover live discovery, cancellation, pairing and trusted-source lookup.

Run the local Python checks with `python3 -m unittest discover -s tests -p 'test_pair*.py' -v`. Build the sample/test APKs normally, then run `TailscaleDiscoveryTest` and `LanSshDiscoveryTest`. `TailscaleDeviceTest` requires the explicit `tailscaleHost` instrumentation argument. Its pairing method additionally requires `tailscalePair=true` and a short-lived QR PNG in app cache at `tailscale-pair.png`; it deliberately retains the newly paired profile. Do not run it against an unrelated user's device or publish QR payloads/logs.

References: [Tailscale CLI](https://tailscale.com/docs/reference/tailscale-cli), [MagicDNS](https://tailscale.com/docs/features/magicdns).

### tmux picker regression found during device acceptance

The Mac's non-interactive SSH environment had no UTF-8 locale. In that environment, `tmux list-sessions` replaced tab separators and non-ASCII names with underscores; the old tab parser silently discarded every row. The picker now uses `tmux -u` and puts numeric fields before the session name with ASCII space separators. Names containing spaces, underscores and Chinese remain intact, and malformed output raises a load error instead of appearing as an empty list.

`TmuxSessionsTest` covers parsing and malformed output on API 27 and the physical phone. `TmuxDeviceTest` accepts `tmuxHost` for an existing saved profile: it creates its own temporary remote session, verifies the list and visible picker row, selects it, attaches a real PTY, checks the original shell PID and removes only that fixture. The physical phone passed this flow over both LAN and Tailscale. Existing user sessions and profiles were preserved.
